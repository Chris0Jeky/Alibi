# Issue 785: bounded native draw-stall trace

## Scope and hypothesis

The API 36 emulator smoke has intermittently timed out WebView evaluation while its UI heartbeat is stale and the sampled main stack is in `HardwareRenderer.nSyncAndDrawFrame`. The stack locates the observed stall; it does not establish whether guest scheduling, the emulator host, graphics composition, WebView or app rendering initiated it. The additional #922 timeout after its controlled unchanged-source rerun remains evidence of the unresolved issue, not an app fix.

The existing native smoke now attempts a Perfetto capture immediately before the unchanged Gradle instrumentation. The existing workflow already retains `test-results/native` even on failure. The captured guest ring includes scheduling switch/waking events, graphics, view, window and SurfaceFlinger categories and process metadata. The app's debug package is selected for app atrace events. The runner still uses its existing SwiftShader emulator, test selection, APK binding, deadlines, assertions, logcat and exit status.

## Bounds and reading the evidence

The detached session has a 600,000 ms hard duration, a 32 MiB ring and an explicit stop in the existing exit cleanup. Start, stop, guest clock and pull commands have individual timeouts; the pull has a separate 64 MiB file-size cap. Diagnostic failures are reported but do not replace the instrumentation result. Cleanup attempts a pull even if stop fails or the session expired; such a file may be incomplete. A failed or empty pull is removed. A run that fails before the trace attempt records `start=not_attempted`.

Each invocation attempts a fresh `test-results/native/draw-trace.XXXXXX/` directory and prints its basename as `native trace output=...`; this identifies the current capture if older directories remain. If directory creation or status initialization fails, it prints `native trace output=unavailable`, skips tracing and preserves the smoke outcome; existing files are not current evidence. The selected directory may contain `draw-trace.pftrace`, `draw-trace-status.txt` and `draw-trace-commands.log`. Status records GitHub run ID/attempt when available, source SHA, the expected **debug** APK digest from the existing audit, host UTC and guest uptime before start/stop, start-return guest uptime, configured limits and command outcomes. `start=ok` only means the start command returned successfully; `pull=ok` only means a nonempty file was copied. Neither establishes that every data source was supported, the file is complete, or the failing interval is retained. Check the trace's actual clock snapshots, source tracks and coverage against the existing `AlibiNativeSmoke` elapsed-realtime stage/heartbeat/timeout log. A long Gradle setup or overwritten ring can leave the test interval outside the trace; an expired/failed stop or unavailable trace is inconclusive. Tracing adds overhead and may affect an intermittent race.

If the relevant interval is present, compare guest UI/RenderThread and SurfaceFlinger scheduling and graphics slices between a failing and a passing run. A prolonged runnable-but-unscheduled interval supports a scheduling hypothesis; blocked/sleeping or CPU-running patterns call for different investigation. Guest scheduling alone cannot prove host starvation, GPU-fence cause or physical-device behavior. A trace without the stall does not refute an intermittent cause. Perfetto documents [detached capture and stop](https://perfetto.dev/docs/concepts/detached-mode), [scheduler events](https://perfetto.dev/docs/data-sources/cpu-scheduling) and [Android on-device capture](https://developer.android.com/tools/perfetto).
